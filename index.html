貸し借り台帳 バイト先の複数店舗で運用中

流れて消えていた貸し借りを、URL一本の台帳に

バイト先のバーでは、店舗をまたいだ物の貸し借りをグループチャットに手打ちで流していた。誰が何をどこに貸したのかは遡らないと分からず、返し忘れても気づけない。これを、スタッフがURLを開くだけで記録・確認できる台帳に置き換えた。運用費はかからず、他店のスタッフにログインを求めない。

01課題

情報は流れていた。ただ、残っていなかった

問題は「共有していないこと」ではなく、共有の形が検索も集計もできないことだった。自分の店・相手の店・借りた物を毎回文章で書くので、書き方は人によって変わる。返却の連絡は別のタイミングで流れるため、どれが未返却なのかは誰も把握していない。

02設計判断

技術より、導入の摩擦をどこまで削れるかで決めた

使うのは自分ではなく他店のスタッフで、業務時間中の片手間に触る。アカウント登録や初期設定を求めた時点で使われなくなる。判断の軸はすべてそこに置いた。

論点採用見送り理由
基盤 Apps Script + スプレッドシート 専用サーバー・BaaS 運用費が発生せず、データは本人のドライブに残る。管理者が引き継げる形になる
認証 なし（匿名で読み書き） Googleログイン必須 他店に配る前提。ログイン要求が導入の最大の障壁になる
店舗一覧 事前登録なし・自動蓄積 全店を先に登録 取引先の店舗数が多く、初期登録の作業が運用開始そのものを止める
表記ゆれ 正規化 + 候補確認 機械による自動統合 別の店を勝手に混ぜる事故は、分裂よりも損害が大きい。機械は候補まで、判断は人に残す
移行 共有用テキストを自動生成 即日の完全移行 従来の運用と並走できないと定着しない。台帳に記録しつつ、これまで通りチャットにも流せる
なりすまし対策 店舗ごとの合言葉（初めて名乗った人が決める） 店舗ごとのログインアカウント 他店を騙って「借りた」記録を作れる穴だけを塞ぐ。合言葉はハッシュ化し、平文は誰も見られない
03画面

入力は品名と数量だけで終わる

自分の店と担当者名は端末が覚える。相手の店はよく使う順にボタンで並ぶ。単位は品名から前回の値を引き継ぐ。結果として、2回目以降に手で打つのは品名と数量だけになる。

数量には必ず単位を添える。「緑茶1本」と「緑茶1ケース」では話が違うのに、文章で流していた頃はどちらか分からなかった。

04権限

認証を入れる代わりに、書ける内容を絞った

URLを配る以上、誰がアクセスしてくるかは制御できない。ログインを課すと導入の敷居が上がって使われなくなるので、操作できる範囲そのものを狭めて不正な記録が成立しないようにした。

  • 記録できるのは「うちが借りた」だけ。貸した側の記録は相手の店が登録する。どの記録も登録者自身の店を借主とする自己申告になるので、他店に身に覚えのない貸し借りを作れない。サーバー側で借主を登録者の自店に固定しているため、APIを直接叩いても貸した側の記録は作れない
  • 他店になりすまして「借りた」記録を作れないよう、店舗ごとに合言葉で守る。初めてその店を名乗るときに決めた合言葉が、以後その店として振る舞うための鍵になる。ハッシュ化して保存するので、平文はスプレッドシートを直接見ても、後述の管理者でも分からない
  • 返却を確定できるのは貸した側だけ。物を受け取るのは貸した側なので、借りた側が自分で「返した」と記録できるのはおかしい。借りた側の画面には返却ボタンを出さず、誰が確認するかだけを表示する
  • 削除できるのは登録した端末だけ。端末ごとの識別子を記録に残し、他人の記録には削除ボタンを出さない。直接APIを叩いても拒否される

どれも暗号的な認証ではなく、操作の向きを一方向に固定することで成り立たせている。小さな信頼関係のある集団では、認証基盤を用意するよりこちらの方が導入も運用も軽い。

唯一パスワードを使うのが管理者ログインで、忘れた合言葉のリセットと、トラブル時の記録の代理削除・返却確定だけができる。多数派の操作は無認証のままにし、なりすましという一点だけを塞ぐ最小限の追加にとどめた。管理者であっても各店舗の合言葉そのものは見られない。

05名寄せ

同じ店が別々に増えていかないための七層

店舗名を自由入力にした以上、同じ店が違う書き方で分裂するのが最大の失敗要因になる。機械が確実に判断できるところだけ自動で寄せ、曖昧なところは人に聞き、それでも漏れたら後から直せるようにした。番号は介入の度合いの順に並んでいる。

  1. 自動で統合 — 確認なし

    照合キーによる正規化

    全角半角の統一、大文字小文字、カタカナからひらがなへの寄せ、記号と長音の除去。文字種の違いだけなら確実に同一と判断できる。

    ﾐﾅﾄ / ミナト / み な と / ミ・ナ・ト → みなと
  2. 候補を提示 — 人が判断

    近い名前の検出

    編集距離と包含関係で、打ち間違いや語尾違いを拾う。

    みなど → 候補「みなと」　　みなと本店 → 候補「みなと」
  3. 候補を提示 — 人が判断

    英字表記とカタカナ表記の橋渡し

    文字としては無関係なので正規化では絶対に繋がらない。書記体系が異なる相手に限りカナ側をローマ字化し、連続母音をまとめて長音の差を吸収してから比較する。

    さくら → sakura　　SAKURA → sakura　　ローマ字にすると一致する
  4. 候補を提示 — 人が判断

    業態名の有無

    「バー」「スナック」などは書く人によって付いたり付かなかったりする。前後から外した形でも突き合わせる。

    バーさくら → さくら → sakura ＝ SAKURA　　スナックみなと ⇔ みなと
  5. 一度で終わらせる — 学習

    確認の結果を覚える

    候補提示はその場の提案でしかないので、放っておくと同じ確認が毎回出る。「これと同じ店だ」と選ばれた表記はその店舗の別名として保存し、以後は完全一致として扱う。誰か一人が一度答えれば全員に効く。

    1回目 ばーさくら → 「SAKURA のことか？」　　2回目以降 ばーさくら → 確認なし
  6. 気づかせる — 事後

    新規店舗の通知

    ここまでをすり抜けた場合に備え、既存にない店舗名で登録されたら完了画面で知らせる。分裂しても当日中に気づける。

  7. 手作業で修復 — 事後

    過去の記録ごと統合

    設定画面から既存の名前に書き換えると、過去の記録すべてが一括で置換され一つの店舗にまとまる。

寄せすぎない制限

業態名を外した残りが2文字未満になる場合は比較しない。これにより バー南 と スナック南 は（残りが「南」の一文字なので）別店舗として扱われる。統合の網を広げるほど、隣の店を巻き込む危険も増える。

06検証

配る前に、他人の環境で確かめた

配布してから壊れているのが分かるのが一番まずい。名寄せは純粋なロジックとして切り出して単体で回し、台帳の読み書きはスプレッドシートをスタブに置き換えて検証し、画面はGoogleにログインしていない状態のブラウザで通した。

デプロイ。URLを保ったまま中身だけ差し替わる

0回

利用者に求めるログイン。URLを開けばそのまま使える

  • 匿名アクセスでの読み書きを実機確認。ログインしていないブラウザから登録・返却・削除まで通し、テストデータは消して戻した
  • スプレッドシートをスタブに置き換えた自動テスト。実装をそのまま動かすので、テストと本番がズレない。この検証で「空行があると別の店舗を削除してしまう」不具合を運用前に発見・修正した
  • デプロイを自動化。コードを直して一行叩けば反映される。公開前には実店舗名の混入を機械的に検査して、見つかれば公開を中止する
07応用

取り出せる型

この案件で作った判断と部品は、次の現場にそのまま持っていける。

  • ログイン不要の業務ツールを無料で配る型。Apps Script のウェブアプリを匿名公開にし、データは依頼主のドライブに置く。小規模な現場では、認証基盤を用意するより導入が早く、引き継ぎも効く
  • 認証は最小限に、大半は操作の向きを固定する設計。誰が触るか制御できない場でも、書ける内容と操作できる相手を絞れば、不正な記録そのものが成立しなくなる。それだけでは塞げない「なりすまし」のような穴にだけ、店舗ごとの合言葉という最小単位のパスワードを足す
  • 日本語の表記ゆれを吸収する名寄せ。正規化キー・ローマ字化・接頭接尾語の除去・別名の学習を段階的に重ねる構造は、店舗名に限らず取引先名や商品名でもそのまま使える
  • 既存運用と並走させる移行設計。新しい仕組みから旧来の共有形式を出力できるようにして、切り替えの決断を利用者に迫らない
